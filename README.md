# gen-service

Сервис генерации: принимает заказ, списывает токены, отдаёт задачу провайдеру,
при отказе идёт к следующему, если отказали все — возвращает токены. Каждое движение
денег происходит ровно один раз.

Документы: [оригинальное задание](docs/00-task.md),
[что делает сервис простыми словами](docs/01-overview.md),
[первичный разбор задания и открытые вопросы](docs/02-initial-analysis.md).
Принятые решения собраны ниже, в разделе [«Решения по неоднозначностям»](#решения-по-неоднозначностям-задания).

## Запуск

```bash
docker compose up -d --build
```

| Сервис    | Что это                                         | Порт на хосте |
|-----------|-------------------------------------------------|---------------|
| `db`      | PostgreSQL 16                                   | 5432          |
| `migrate` | `alembic upgrade head`, затем завершается       | —             |
| `api`     | сервис, `uvicorn --workers 4`                   | 8000          |
| `alpha`   | фейковый провайдер                              | 8001          |
| `beta`    | фейковый провайдер (тот же код, другое имя)     | 8002          |
| `payments`| фейковая платёжка для UI                        | 8003          |

`api` стартует только после успешного `migrate`, поэтому 4 воркера не мигрируют базу
наперегонки. Swagger: http://localhost:8000/docs

### UI

http://localhost:8000/ — простая страница без сборки и внешних зависимостей
([app/ui/index.html](app/ui/index.html)), её отдаёт сам сервис. На ней можно:

- выбрать пользователя и пополнить баланс (+10/+50/+100);
- выбрать модель и референсы и увидеть, какие ноги их примут;
- отправить заказ и смотреть, как задача идёт по ногам: статусы попыток, ошибки,
  возврат, поздний результат;
- смотреть журнал операций.

Готовность задач UI узнаёт **опросом** `GET /users/{id}/tasks`: раз в 1,5 с, пока есть
активные задачи, и раз в 6 с в остальное время. На скрытой вкладке опрос не идёт.
При генерации 2–20 с этого достаточно, а сервер остаётся без состояния соединений.

Пополнение идёт через фейковую платёжку (`payments`, порт 8003). Браузер не может
подписать вебхук оплаты, ведь секрет должен оставаться на сервере, а добавлять в сервис
лазейку «начислить без оплаты» не хочется. Поэтому UI «оплачивает» в фейке, и тот, как
настоящая платёжка, присылает подписанный `POST /webhooks/payments`. Галочка
«×5 вебхуков» шлёт один и тот же вебхук 5 раз одновременно: видно, что начисление одно.

Для UI добавлены `GET /models` (каталог с ногами) и `GET /users/{id}/tasks`
(последние задачи с историей попыток).

Пример: пополнить баланс пользователя 1, заказать картинку, посмотреть результат.

```bash
BODY='{"payment_id":"p-1","user_id":1,"tokens":50,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac dev-secret | awk '{print $NF}')
curl -s localhost:8000/webhooks/payments -H "X-Signature: $SIG" -H 'Content-Type: application/json' -d "$BODY"

curl -s localhost:8000/generate -H 'Content-Type: application/json' \
  -d '{"user_id":1,"model_slug":"image-fast","prompt":"a cat in space","ref_images":[]}'
# {"task_id":"..."} — через 2–20 с задача completed
curl -s localhost:8000/tasks/<task_id>
curl -s localhost:8000/users/1/balance
```

## Тесты

Тесты ходят в живой стек из compose: настоящую базу, API в 4 воркера и фейковых провайдеров.

```bash
docker compose up -d --build
docker compose run --rm tests          # ~2,5 мин: тесты правила 6 честно ждут 60 с
```

Быстрый прогон с таймаутом провайдера 5 с (переменную нужно передать обеим командам):

```bash
PROVIDER_TIMEOUT_SECONDS=5 docker compose up -d
PROVIDER_TIMEOUT_SECONDS=5 docker compose run --rm tests   # ~30 с
```

Перед каждым тестом оба фейка переключаются в «быстро и без сбоев», и тест включает
только тот сбой, который проверяет. У каждого теста свой случайный пользователь,
поэтому базу между прогонами чистить не нужно. Каждый тест, который двигает деньги,
проверяет, что баланс равен сумме журнала.

Обязательные тесты из задания:

| Требование | Тест |
|---|---|
| 20 одновременных одинаковых вебхуков оплаты → одно начисление | `test_payments.py::test_20_concurrent_identical_payments_credit_once` |
| 10 одновременных failed на последней ноге → один возврат | `test_failover.py::test_10_concurrent_failed_on_last_leg_refund_once` |
| Отказ первой ноги → задача завершается на второй, в истории две попытки | `test_failover.py::test_first_leg_fails_task_completes_on_second` |
| Поздний completed после срабатывания сторожа | `test_watchdog.py::test_late_completed_while_next_leg_runs_…`, `…_after_refund_does_not_deliver_result` |

Остальное: 503 и таймаут на `POST /tasks`, модерация и `skip_on_moderation`, payload,
лимит референсов при переходе, дубли вебхуков подряд и одновременно, 400/402/404/429,
гонка за лимит активных задач, восстановление после падения процесса.

## Как устроено

```
POST /generate ── одна транзакция: проверки → списание → задача + попытка pending
      │
      ▼ (после коммита, в фоне)
 dispatch ── POST /tasks провайдеру
      │            ├─ 202 ─────────► submitted, ждём вебхук до PROVIDER_TIMEOUT
      │            └─ 5xx/таймаут ─┐
      ▼                            │
 вебхук completed ─► задача completed
 вебхук failed ────────────────────┤
 сторож: дедлайн истёк ────────────┤
                                   ▼
                     fail_locked: payload? ── да ──► failed + возврат
                                   │ нет
                          есть подходящая нога? ── нет ──► failed + возврат
                                   │ да
                          новая попытка pending ──► dispatch
```

Все источники отказа (вебхук failed, синхронная ошибка, сторож) ведут в одну функцию
`orchestrator.fail_locked`. Поэтому правила перехода по ногам описаны в одном месте.

Статусы задачи: `pending` (ждёт отправки) → `running` (отправлена, ждём вебхук) →
`completed` | `failed`. Статусы попытки: `pending` → `dispatching` → `submitted` →
`completed` | `failed` | `timed_out` | `cancelled`.

Код:

| Файл | Что там |
|---|---|
| [app/ledger.py](app/ledger.py) | единственное место, где меняется баланс |
| [app/orchestrator.py](app/orchestrator.py) | создание задачи, переход по ногам, завершение, правило 6 |
| [app/dispatcher.py](app/dispatcher.py) | отправка попыток провайдерам |
| [app/watchdog.py](app/watchdog.py) | сторож |
| [app/payments.py](app/payments.py) | платёжный вебхук |
| [fake_provider/main.py](fake_provider/main.py) | фейковые провайдеры |
| [fake_payments/main.py](fake_payments/main.py) | фейковая платёжка для UI |
| [app/ui/index.html](app/ui/index.html) | UI |

## «Ровно один раз» для начисления, списания и возврата

**Основа — уникальный ключ в журнале.** Любое изменение баланса — это вставка строки
в `ledger_entries` с `idempotency_key`: `payment:<payment_id>`, `charge:<task_id>` или
`refund:<task_id>`. Вставка идёт через `ON CONFLICT DO NOTHING`, а `users.balance` сдвигается
в той же транзакции и только если строка вставилась ([app/ledger.py](app/ledger.py)).
Повтор операции упирается в `UNIQUE` и ничего не меняет. Баланс всегда равен сумме журнала,
а `CHECK (balance >= 0)` не даёт уйти в минус.

Гарантию даёт база, а не проверка «а нет ли уже такой операции» в коде: между такой
проверкой и вставкой успел бы пройти соседний запрос. При одновременной вставке одного
ключа PostgreSQL заставляет второй запрос дождаться коммита первого и вернуть конфликт.
Если первый откатился, вставит второй.

**Начисление.** 20 одинаковых вебхуков оплаты в 4 воркера дают одну вставку
`payment:<payment_id>`. Остальные отвечают 200 `duplicate`, чтобы платёжка перестала
ретраить.

**Списание.** Делается в транзакции `/generate` под блокировкой строки пользователя.
Ключ `charge:<task_id>` уникален, так как `task_id` новый.

**Возврат** защищён дважды:

1. Все переходы задачи идут под блокировкой её строки (`SELECT … FOR UPDATE`). Из 10
   одновременных failed первый переводит задачу в failed. Остальные по очереди видят,
   что попытка уже не активна, и ничего не делают (ответ `ignored`).
2. Даже если переход случится дважды, `refund:<task_id>` в журнал попадёт один раз.

В переходах задачи порядок блокировок везде одинаковый: задача, потом попытка, потом пользователь.
Поэтому вебхук, отправщик и сторож не устраивают друг другу дедлок.

## Что будет при падении процесса посреди обработки

Каждый шаг — короткая транзакция, а то, что нужно сделать после неё, уже записано в базе.
Поэтому после любого падения есть кому продолжить.

| Где упал процесс | Что в базе | Кто продолжит |
|---|---|---|
| Посреди вебхука (провайдера или оплаты), до коммита | ничего не изменилось: транзакция откатилась | провайдер или платёжка не получили 2xx и пришлют вебхук снова |
| После коммита вебхука, до ответа | изменение есть | повторный вебхук станет дублем: 200 `ignored`/`duplicate`, без второго перехода или начисления |
| После коммита failed, до отправки следующей ноги | новая попытка `pending` | сторож отправит её через `PENDING_DISPATCH_GRACE_SECONDS` |
| После коммита `/generate`, до отправки | попытка `pending`, деньги списаны | сторож отправит её |
| Посреди `POST /tasks` провайдеру | попытка `dispatching` с арендой (`deadline_at`) | аренда истечёт, сторож признает попытку `timed_out` и поведёт задачу дальше |
| Провайдер принял задачу, но процесс не успел записать `external_id` | попытка `dispatching` | то же; поздний вебхук с неизвестным `external_id` получит 404 и после ретраев будет брошен |

Отправка провайдеру никогда не идёт внутри транзакции. Держать блокировку на время
HTTP-запроса нельзя, а захват попытки (`UPDATE … WHERE status = 'pending'`) атомарный.
Поэтому одну попытку не отправят дважды, даже если до неё дотянутся несколько процессов.

## Поздний completed (правило 6)

Ситуация: сторож перестал ждать попытку (`timed_out`), а потом от провайдера всё-таки
пришёл completed. Запрещённый исход — «и результат, и возврат», поэтому решение зависит
от того, был ли уже возврат.

- **Задача ещё в работе на другой ноге.** Возврата не было и уже не будет. Отдаём готовый
  результат: задача `completed`, текущая попытка `cancelled`, её собственный вебхук потом
  будет проигнорирован. Пользователь получает результат раньше, а платим мы провайдеру
  за ту работу, которая уже сделана.
- **Задача уже `failed`, токены вернули.** Результат пользователю не выдаём. Списать
  повторно нельзя: денег может не хватить, а пользователь уже видел отказ. Результат
  сохраняется в истории попытки (`result_url`, `late_result_at`), чтобы было видно,
  что он пришёл.

Поздний failed по снятой попытке просто игнорируется: задачу по ней уже повели дальше.

Реализация: `orchestrator.complete_late`. Тесты: `tests/test_watchdog.py`.

## Сторож в 4 процессах

Сторож запущен в каждом воркере, поэтому падение одного процесса не останавливает
присмотр за задачами. Раз в `WATCHDOG_INTERVAL_SECONDS` он:

1. Берёт попытку с истёкшим дедлайном вместе с блокировкой её задачи через
   `FOR UPDATE SKIP LOCKED`. Другой процесс эту задачу пропускает, а не обрабатывает
   второй раз. Попытка становится `timed_out` и идёт в `fail_locked` как отказ `technical`.
2. Отправляет брошенные `pending`-попытки. Их могут найти несколько процессов,
   но отправит один: захват атомарный.

## Решения по неоднозначностям задания

| Вопрос | Решение |
|---|---|
| Когда нога подходит | `len(ref_images) <= max_ref_images`; неподходящие ноги пропускаются и при переходе |
| `skip_on_moderation`: «предыдущая отказала по модерации» | любой отказ `moderation` в истории задачи: контент уже признан проблемным |
| Порядок проверок `/generate` | 404 модель → 400 нет ноги → 404 пользователь → 429 → 402; всё до списания |
| Лимит 3 активных задачи при гонке | блокировка строки пользователя перед подсчётом |
| Ответ `/generate` | 202 `{task_id}` сразу, отправка провайдеру в фоне |
| Синхронный ответ провайдера не 202 (5xx, 4xx, таймаут, обрыв) | как `technical`: следующая нога |
| Провайдер молчит | `timed_out` с `error_type = technical` |
| Вебхук с неизвестным `external_id` | 404, чтобы провайдер повторил: вебхук мог обогнать запись ответа на `POST /tasks` |
| Статусы оплаты | зачисляем только `succeeded`, остальные — 200 `ignored` |
| Тот же `payment_id` с другой суммой или пользователем | 409, не зачисляем |
| Оплата для неизвестного пользователя | создаём пользователя: регистрации нет, а 404 означал бы потерянный платёж |
| «Последние строки журнала» | 20 строк, новые сверху |
| Как тесты управляют фейками | API управления `PUT /control/behavior` |

## Фейковые провайдеры

Один код ([fake_provider/main.py](fake_provider/main.py)), имя задаёт `PROVIDER_NAME`.
`POST /tasks` отвечает 202 `{"external_id"}`, затем через `delay_min..delay_max` секунд
приходит подписанный вебхук. Недоставленный вебхук (не-2xx) провайдер повторяет.

Поведение меняется на лету, без перезапуска:

```bash
curl -X PUT localhost:8001/control/behavior -H 'Content-Type: application/json' \
  -d '{"failure_rate": 1, "failure_type": "moderation"}'
curl -X PUT localhost:8001/control/behavior -H 'Content-Type: application/json' -d '{}'  # сброс
```

| Поле | Что делает |
|---|---|
| `delay_min`, `delay_max` | задержка вебхука, по умолчанию 2–20 с |
| `failure_rate`, `failure_type` | доля отказов и тип: `technical`, `moderation`, `payload` |
| `sync_failure_rate`, `sync_failure`, `sync_timeout_seconds` | 503 или зависание на сам `POST /tasks` |
| `duplicate_webhook` | `sequential` или `concurrent` — вебхук приходит дважды |
| `drop_webhook_rate` | вебхук не приходит совсем |
| `delay_min` > `PROVIDER_TIMEOUT` | completed после того, как сервис перестал ждать |
| `webhook_retries`, `webhook_retry_delay` | ретраи доставки вебхука |

Поведение фиксируется в момент приёма задачи: смена настроек не трогает задачи,
которые уже в работе.

## Миграции

Схема создаётся только миграциями Alembic ([migrations/versions](migrations/versions)).
ORM-модели в [app/models.py](app/models.py) обязаны с ними совпадать.

| Ревизия | Что делает |
|---------|------------|
| 0001 | таблицы: users, generation_models, model_legs, tasks, task_attempts, ledger_entries |
| 0002 | каталог: image-fast и video-long с их ногами |
| 0003 | демо-пользователи 1, 2, 3 с нулевым балансом |
| 0004 | статусы попытки `dispatching` и `cancelled`, индексы для сторожа |
| 0005 | `task_attempts.late_result_at` для правила 6 |

Применить, откатить, посмотреть текущую:

```bash
docker compose run --rm migrate alembic upgrade head
docker compose run --rm migrate alembic downgrade -1
docker compose run --rm migrate alembic current
```

Добавить следующую (так сделана 0005):

1. Поменять модели в `app/models.py`.
2. Сгенерировать черновик со следующим номером:
   ```bash
   docker compose build
   docker compose run --rm -v "$PWD/migrations:/srv/migrations" -u "$(id -u)" \
     migrate alembic revision --autogenerate --rev-id 0006 -m "add something"
   ```
3. Вычитать и поправить файл руками: autogenerate не видит изменения CHECK-ограничений
   и не пишет миграции данных. Имена ограничений в `op.drop_constraint` оборачивать
   в `op.f(...)`, иначе naming convention применится к имени второй раз.
4. Проверить, что модели и миграции совпадают:
   `docker compose run --rm migrate alembic check` → `No new upgrade operations detected.`
5. Убедиться, что проходят оба: `alembic upgrade head` и `alembic downgrade -1`.

## Схема данных

- `users.balance` — кэш суммы журнала, `CHECK (balance >= 0)`.
- `ledger_entries` — журнал; `idempotency_key UNIQUE`, сумма со знаком.
- `tasks.price` — цена на момент заказа, чтобы вернуть ровно списанное.
- `task_attempts` — история попыток по ногам; `UNIQUE (provider, external_id)` для поиска
  попытки по вебхуку; частичные индексы для сторожа (`deadline_at` у ждущих попыток,
  `created_at` у `pending`).
- Статусы — `text` + `CHECK`, а не PG `ENUM`: значение добавляется обычной миграцией
  с откатом (см. 0004), а `ALTER TYPE … ADD VALUE` не откатывается.
